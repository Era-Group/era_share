Lead Generation — User Manual

Net-new B2B company & decision-maker discovery for the Era Group CRM AI Agents suite.

Module: era_crm_ai_agents_lead_gen  ·  Audience: managers & administrators  ·  Scope: configuration & day-to-day operation

1.Overview

Lead Generation is the top of the sales funnel. Its job is to bring net-new companies (and, optionally, their decision-makers) into the CRM from external data sources, de-duplicate them against what you already have, tag them so they are traceable, and leave them ready for the rest of the suite to work.

What it does

  • Queries external sources (search APIs, business registries) in priority order to discover companies that match your targeting (sectors, regions, size).
  • Uses the suite's AI to read each source's raw response and extract structured firmographics (name, website, city, …).
  • De-duplicates before creating, then creates a res.partner company record, tags it by_lead_generator_agent, and stamps the exact source on x_lead_gen_source.
  • Optionally discovers decision-makers (named individuals) and links them to their company — only when explicitly enabled.
  • Runs on a daily schedule, inside hard daily and cost caps, with every decision written to the audit log.

What it does not do

  • It is not Enrichment (#2). Enrichment completes and verifies records that already exist; Lead Generation brings in records that do not exist yet. They are separate modules with separate jobs.
  • It does not send any outreach. It only creates records; messaging is governed by the Compliance layer (#1) and other agents.
  • It does not guarantee data quality. Extraction is best-effort over search results — expect a company name and website far more reliably than a VAT number or sector.
ℹ️ Honest expectations (read this)

Out of the box, with the right API tokens, this module reliably finds companies. The decision-maker (people) side is intentionally limited today: most contact-data providers are not yet implemented and LinkedIn is a deferred stub (see §4). Treat the company feed as a "suggested companies" list a human reviews — not a finished, ready-to-call contact database.

2.Before you start — prerequisites

  • Base module installed. Lead Generation depends on era_crm_ai_agents_base (the shared agent registry, AI Compliance Guard, usage/cost tracking and audit log). It is the only hard dependency.
  • Python requests must be available on the server (it ships with Odoo; declared as an external dependency).
  • A manager role. All configuration and the source list are visible only to the AI Agents Manager group. Salespeople can see sources read-only; they cannot change them.
  • API tokens in the server environment for any source you intend to use — never in the database (see §4).
⚠️ Everything ships OFF by default — and that is deliberate

On a fresh install the master switch era_crm_ai_agents_lead_gen.enabled is OFF, every one of the 18 seeded sources is inactive (active = False), and decision-maker fetching is OFF. Nothing queries the network, nothing spends money, and nothing creates records until a manager deliberately turns it on. This is the conservative, review-first posture required by PDPL (§10).

4.Activating data providers

A provider (or "source") is one external data service. The engine only queries a source when all three of these hold — this is the token-presence model:

  1. Active — the source record is toggled active = True (a manager decision; everything ships inactive).
  2. Token present — the environment variable the source names in env_key_param resolves to a value on the server. The secret itself is never stored in Odoo — only the variable's name is.
  3. In scope — for decision-maker sources, the separate fetch_decision_makers toggle must also be ON.

An active source whose token is missing is skipped — never silently: a blocked audit entry is written (unless you set the missing-token policy to silent). You manage sources under CRM AI Agent Base → Lead Generation → Sources: drag to re-order priority, toggle active inline, and read the live Token indicator.

💡 How to switch a source on

1) Put the API key in the server environment under the variable the source names (e.g. ERA_LEADGEN_SERPAPI_KEY) and restart the server so it is picked up. 2) Open the source in Sources, confirm Token = ✓, and toggle it Active. 3) Make sure the master toggle is ON. The source now enters the waterfall by its priority.

5.Running a discovery — manual run

  1. Set your targeting. In Lead Generation → Settings, fill Target Sectors and Target Regions (e.g. Construction / Riyadh, Jeddah). Optionally set size.
  2. Activate at least one working source with its token present (see §4) — for example SerpAPI or OpenCorporates.
  3. Turn the master toggle ON (Enable Lead Generation). Leave Fetch Decision-Makers OFF for a company-only run.
  4. Trigger a run. The engine runs the same code path whether triggered manually or by the cron. (Day-to-day, most teams simply let the daily cron do it — see §6.)
  5. Find the results in CRM. New companies appear as res.partner records, each carrying the by_lead_generator_agent tag and an x_lead_gen_source stamp naming the exact provider. The fastest view is Lead Generation → Externally-Sourced Records, which lists everything the engine created, grouped by source.
ℹ️ The waterfall, briefly

Within a run the engine tries eligible sources in priority order and stops at the first that returns results (the "waterfall"). One run therefore yields one source's batch per category — expect a handful of companies per run, not hundreds.

6.Running automatically — the daily cron

A scheduled action, "Lead Generation: Scheduled fetch", runs once per day and calls the same entry point as a manual run, unattended.

  • Runs as a dedicated, non-superuser service account — the Lead Generation Bot (login lead_gen_bot) — so creation and de-dup obey normal access rules rather than running as the administrator.
  • Gated by the master toggle. If …lead_gen.enabled is OFF, the scheduled run exits immediately and does nothing. The single master switch governs scheduled runs too.
  • Respects both caps — the daily record cap and the monthly cost cap (§8).
  • Never errors out. Because it runs unattended, any guard block (consent, cost cap, a paused agent) becomes a skip-with-audit — the job finishes cleanly and leaves an audit trail instead of failing.
💡 Turning the schedule on/off

The simplest control is the master toggle: enable the module and the daily run starts producing; disable it and the cron keeps firing but does nothing. The cron record itself can also be deactivated by an administrator under Settings → Technical → Scheduled Actions if you want to stop it entirely.

ℹ️ After install

New scheduled actions require a full server restart to register (an upgrade alone is not enough). If the cron does not appear, restart the Odoo service.

7.The Enrichment hand-off

Lead Generation does not call the Enrichment module directly — the hand-off is intentionally soft and dependency-free. Every record the engine creates is already tagged (by_lead_generator_agent) and source-stamped (x_lead_gen_source). That tag/stamp is the hand-off: Enrichment (#2), once present, scans for these records on its own schedule and completes/verifies them. No direct call, no hard dependency, no coupling.

ℹ️ Why "soft"

It keeps the two modules independent — Lead Generation installs and works whether or not Enrichment is present, and you can isolate or purge the entire externally-sourced population in one move by filtering on the tag or the source field.

8.Caps & cost control

Daily record cap (…daily_cap, default 50)

This limits how many records the engine may create per day, and it is dual-enforced:

  • Before each source call — if the day's count already meets the cap, the engine does not even fetch (zero spend).
  • At each record creation — a last-line check, so two near-simultaneous runs cannot both slip past and overshoot.

Fail-safe behaviour: a value of 0 or less means unlimited (explicit opt-out); a missing or unreadable value blocks the run (so the cap can never silently disappear).

Monthly cost cap (suite-wide)

Spend is bounded by era_crm_ai_agents.monthly_cost_cap (default 100.0 USD), enforced by the base. The Lead-Gen engine additionally re-checks this limit before each source call, so once the month's spend is exhausted it stops fetching rather than continuing to spend. Each run records both halves of its cost: the source-API call (usage_type = source_api) and the AI extraction (usage_type = llm).

What happens when a cap is hit

  • Attended (manual) run, over the cost cap: the run fails fast with a clear error so you know to act.
  • Unattended (cron) run, over a cap: the run skips with an audit entry (cost_cap_exceeded) and finishes cleanly — it never errors the scheduler.

9.Audit & monitoring

Every meaningful decision is written to the suite's append-only audit log (CRM AI Agents → Configuration → Audit Log, manager-only). What you will see for Lead Generation:

Event typeWhen it is written
external_contactA new company or decision-maker record was created (links to the record; an individual's name is not stored in the entry — only a reference).
blockedAn active source was skipped because its token was missing (the never-silent skip).
source_fetch_failedA source call failed. Only the host and the error type are logged — never the URL, query string, or token.
cost_cap_exceededA run or creation was stopped by the daily cap or the monthly cost cap.
ai_request / otherPer-attempt outcomes (success / skip / empty / data-left-region flag) and run start/end summaries.
💡 Quick health check

Filter the audit log by agent or event type. A healthy enabled run shows a "run start", one or more per-source attempts, external_contact rows for what it created, and a "run end" summary. Lots of blocked rows means active sources are missing their tokens.

10.PDPL & compliance

⚠️ Read before enabling decision-maker discovery

Discovering decision-makers means processing the personal data of named individuals who have not consented — and the extraction step sends source content to an international AI provider. This is the heaviest activity in the module under Saudi PDPL. A lawful basis must be reviewed and approved by your legal/DPO function before you enable it.

The module is designed for compliance but does not assert it:

  • Defaults are deliberately conservative — the master toggle, people-fetch, and every source are OFF on install.
  • People-fetch sits behind a second, separate toggle so it can never be switched on by accident with the master switch.
  • Company data is treated as lighter; individuals are stored as linked contacts so retention/erasure can be applied to them separately.
  • Cross-border data movement is flagged in the audit when a non-local source is used.
  • The notice/consent posture settings record your stance; the Compliance layer (#1) enforces "no outreach without consent" downstream.
⚠️ Enabling is not the same as being compliant

Turning the toggles on does not, by itself, make the behaviour lawful. The conservative defaults exist so that the decision is a deliberate, reviewed one — not a default. There is no approved Era Group PDPL reference wired in; that review is yours to complete.

11.Troubleshooting / FAQ

"I enabled the module but no leads appear."

Most often no source is eligible. Check, in order: is at least one source Active? Does that source show Token = ✓ (its env var is set and the server was restarted)? Is the source a company source (verification sources never run in discovery)? Is the daily cap already reached for today? The audit log will show blocked (missing token) or cost_cap_exceeded (cap) rows that explain it.

"A specific provider isn't running."

If it is Apollo/Lusha/RocketReach/SignalHire or LinkedIn, that is expected — those are not implemented yet (§4). For a Saudi registry, set its …_URL environment variable. For a web-search provider, confirm the key env var (and, for Google CSE, the …_CX id). A token-less active source is skipped with a blocked audit entry.

"The daily cron didn't run / didn't create anything."

Three usual causes: (1) the master toggle is OFF — the cron fires but exits immediately; (2) the cron was never registered because the server was not restarted after install; (3) a cap was hit — look for cost_cap_exceeded in the audit. The cron never throws an error; it always finishes and leaves a trail.

"I hit the daily cap."

Expected and safe — the engine stops creating for the day. Raise …daily_cap if you genuinely want more per day, set it to 0 for unlimited (not recommended while you are still trusting the data), or simply wait for the next day.

"A legitimately new company wasn't created — it looks like a duplicate."

De-dup matches on email, website domain, VAT, or name + region. A bare name match alone never blocks creation, so this is rare; if it happens, the incoming record genuinely matched an existing one on a strong key. In skip mode nothing is changed; switch to update if you want blank fields on the existing record filled.

"Could a source call leak our API key into the logs?"

No. On any failure only the host and the error type are logged — never the full URL, query string, or raw exception — so query-string tokens (SerpAPI, Google CSE) cannot appear in the server log or the audit.

"Why is decision-maker discovery so limited?"

By design and by status: the people-search providers that need it are either not yet implemented (POST APIs) or deferred (LinkedIn), and the capability is the most sensitive under PDPL. Company discovery is the supported path today.

12.Glossary

  • Provider / source — one external data service (a search API, a registry, a contact-data API). Described by one record under Sources.
  • Token-presence — a source is only used when its named environment variable resolves to a value; the secret is never stored in Odoo, only the variable's name (env_key_param).
  • Waterfall — trying eligible sources in priority order and stopping at the first that returns results.
  • Skip-with-audit — when something cannot proceed (missing token, hit cap, guard block), the engine skips that step and writes an audit entry instead of failing — never a silent skip.
  • Dual enforcement — the daily cap is checked both before fetching and again at each record creation, so it cannot be overshot.
  • Soft hand-off — passing records to Enrichment purely via the tag + source stamp, with no direct call or code dependency.
  • Lead Generation Bot — the dedicated non-superuser account the daily cron runs as, so scheduled work obeys normal access rules.
