Lead Generation — User Manual

Net-new B2B company & decision-maker discovery for the Era Group CRM AI Agents suite.

Module: era_crm_ai_agents_lead_gen · Audience: managers & administrators · Scope: configuration & day-to-day operation

1.Overview

Lead Generation is the top of the sales funnel. Its job is to bring net-new companies (and, optionally, their decision-makers) into the CRM from external data sources, de-duplicate them, tag them so they are traceable, and leave them ready for the rest of the suite.

What it does

  • Queries external sources (search APIs, business registries) in priority order to discover companies matching your targeting (sectors, regions, size).
  • Uses the suite's AI to read each source's raw response and extract structured firmographics.
  • De-duplicates before creating, then creates a res.partner company, tags it by_lead_generator_agent, and stamps the source on x_lead_gen_source.
  • Optionally discovers decision-makers and links them to their company — only when explicitly enabled.
  • Runs daily inside hard daily and cost caps, with every decision written to the audit log.

What it does not do

  • It is not Enrichment (#2). Enrichment completes existing records; Lead Generation brings in records that do not exist yet.
  • It sends no outreach — it only creates records.
  • It does not guarantee data quality; expect a company name and website far more reliably than a VAT number.
ℹ️ Honest expectations (read this)

With the right API tokens this module reliably finds companies. The decision-maker (people) side is intentionally limited today — most contact-data providers are not yet implemented and LinkedIn is a deferred stub (see §4). Treat the company feed as a "suggested companies" list a human reviews.

2.Before you start — prerequisites

  • Base module installed. Depends on era_crm_ai_agents_base — the only hard dependency.
  • Python requests available on the server (ships with Odoo).
  • A manager role. Configuration and the source list are visible only to the AI Agents Manager group; salespeople see sources read-only.
  • API tokens in the server environment for any source you use — never in the database (§4).
⚠️ Everything ships OFF by default — deliberately

On a fresh install the master switch era_crm_ai_agents_lead_gen.enabled is OFF, all 18 seeded sources are inactive (active = False), and decision-maker fetching is OFF. Nothing queries the network, spends money, or creates records until a manager turns it on. This is the review-first posture required by PDPL (§10).

4.Activating data providers

A provider is one external data service. The engine queries a source only when all three hold:

  1. Active — toggled active = True (everything ships inactive).
  2. Token present — the environment variable named in env_key_param resolves on the server. The secret is never stored in Odoo — only the variable's name.
  3. In scope — decision-maker sources also need fetch_decision_makers ON.

An active source with a missing token is skipped — never silently: a blocked audit entry is written (unless the policy is silent). Manage sources under Lead Generation → Sources.

💡 How to switch a source on

1) Put the key in the server environment under the variable the source names (e.g. ERA_LEADGEN_SERPAPI_KEY) and restart the server. 2) Open the source, confirm Token = ✓, toggle Active. 3) Ensure the master toggle is ON.

5.Running a discovery — manual run

  1. Set targeting in Settings (e.g. Construction / Riyadh, Jeddah).
  2. Activate a working source with its token present (§4) — e.g. SerpAPI or OpenCorporates.
  3. Turn the master toggle ON. Leave Fetch Decision-Makers OFF for a company-only run.
  4. Trigger a run — same code path as the cron.
  5. Find results in CRM: new companies carry the by_lead_generator_agent tag + an x_lead_gen_source stamp. Use Lead Generation → Externally-Sourced Records, grouped by source.
ℹ️ The waterfall, briefly

The engine tries eligible sources by priority and stops at the first that returns results. Expect a handful of companies per run, not hundreds.

6.Running automatically — the daily cron

The scheduled action "Lead Generation: Scheduled fetch" runs once per day and calls the same entry point, unattended.

  • Runs as a dedicated non-superuser account — the Lead Generation Bot (login lead_gen_bot) — so work obeys normal access rules.
  • Gated by the master toggle — if disabled it exits immediately.
  • Respects both caps (§8).
  • Never errors out — any guard block becomes a skip-with-audit.
ℹ️ After install

New scheduled actions require a full server restart to register.

7.The Enrichment hand-off

Lead Generation does not call Enrichment directly — the hand-off is soft and dependency-free. Every created record is already tagged (by_lead_generator_agent) and source-stamped (x_lead_gen_source); that tag/stamp is the hand-off. Enrichment (#2), once present, scans for them on its own schedule. No direct call, no coupling.

8.Caps & cost control

Daily record cap (…daily_cap, default 50)

Limits records created per day, dual-enforced: before each source call (zero spend if already met) and again at each creation. Fail-safe: 0 = unlimited; missing = blocks.

Monthly cost cap (suite-wide)

Bounded by era_crm_ai_agents.monthly_cost_cap (default 100.0 USD). The engine re-checks it before each source call. Each run records both halves: source (usage_type = source_api) and AI (usage_type = llm).

When a cap is hit

  • Attended (manual) over the cost cap: fails fast with a clear error.
  • Unattended (cron) over a cap: skips with audit (cost_cap_exceeded) and finishes cleanly.

9.Audit & monitoring

Every decision goes to the append-only audit log (CRM AI Agents → Configuration → Audit Log, manager-only):

Event typeWhen
external_contactA company/decision-maker was created (links to the record; an individual's name is not stored).
blockedAn active source skipped for a missing token.
source_fetch_failedA source call failed — only host + error type logged, never the URL or token.

💡 Quick health check

Many blocked rows means active sources are missing tokens. A healthy run shows "run start", attempts, external_contact rows, and "run end".

10.PDPL & compliance

⚠️ Read before enabling decision-maker discovery

Discovering decision-makers means processing personal data of individuals who have not consented, and extraction sends source content to an international AI provider. A lawful basis must be reviewed and approved by your legal/DPO function before enabling it.

The module is designed for compliance but does not assert it:

  • Defaults are conservative — master toggle, people-fetch, and every source are OFF on install.
  • People-fetch sits behind a separate toggle so it cannot be switched on by accident.
  • Individuals are stored as linked contacts so retention/erasure applies separately.
  • Cross-border movement is flagged in the audit.
  • Notice/consent posture settings record your stance; Compliance (#1) enforces "no outreach without consent" downstream.
⚠️ Enabling is not the same as being compliant

Turning toggles on does not make the behaviour lawful. The conservative defaults exist so the decision is a deliberate, reviewed one. There is no approved Era Group PDPL reference wired in; that review is yours.

11.Troubleshooting / FAQ

"I enabled it but no leads appear."

Usually no source is eligible. Check: is a source Active? Token = ✓ (env var set + server restarted)? Is it a company source (verification sources never run in discovery)? Is the daily cap already met? The audit shows blocked or cost_cap_exceeded rows that explain it.

"A specific provider isn't running."

Apollo/Lusha/RocketReach/SignalHire and LinkedIn are not implemented yet (§4). Saudi registries need their …_URL env var. Web-search needs the key (and Google CSE the …_CX id). A token-less active source logs blocked.

"The daily cron didn't run / created nothing."

(1) master toggle OFF; (2) server not restarted after install; (3) a cap was hit (cost_cap_exceeded). The cron never throws — it always finishes with a trail.

"I hit the daily cap."

Expected and safe. Raise …daily_cap, set 0 for unlimited (not recommended early), or wait for the next day.

"A new company looks dropped as a duplicate."

De-dup matches on email, domain, VAT, or name+region; a bare name alone never blocks. In skip mode nothing changes; use update to fill blank fields.

"Could a source call leak our API key into the logs?"

No — on failure only the host and error type are logged, never the URL, query string, or token.

12.Glossary

  • Provider / source — one external data service.
  • Token-presence — a source is used only when its named env var resolves; the secret is never stored, only the name (env_key_param).
  • Waterfall — trying sources by priority and stopping at the first that returns results.
  • Skip-with-audit — skipping a step and writing an audit entry instead of failing; never silent.
  • Dual enforcement — the daily cap is checked before fetching and again at creation.
  • Soft hand-off — passing records to Enrichment purely via the tag + source stamp.
  • Lead Generation Bot — the dedicated non-superuser account the cron runs as.

توليد العملاء المحتملين — دليل المستخدم

اكتشاف شركات (B2B) وصنّاع قرار جُدد بالكامل ضمن منظومة وكلاء الذكاء الاصطناعي لمجموعة Era.

الوحدة: era_crm_ai_agents_lead_gen · الجمهور: المديرون والمسؤولون · النطاق: الإعداد والتشغيل اليومي

١.نظرة عامة

توليد العملاء المحتملين هو رأس قُمع المبيعات. مهمته جلب شركات جديدة بالكامل (واختياريًا صنّاع القرار فيها) إلى نظام إدارة العلاقات من مصادر بيانات خارجية، ثم منع التكرار، ووسمها لتكون قابلة للتتبّع، وتركها جاهزة لبقية المنظومة.

ما الذي يقوم به

  • يستعلم من مصادر خارجية (واجهات بحث، سجلات تجارية) بترتيب الأولوية لاكتشاف الشركات المطابقة لاستهدافك (القطاعات، المناطق، الحجم).
  • يستخدم الذكاء الاصطناعي للمنظومة لقراءة الاستجابة الخام لكل مصدر واستخراج بيانات الشركات بشكل منظّم.
  • يمنع التكرار قبل الإنشاء، ثم ينشئ سجل شركة res.partner، ويسمه by_lead_generator_agent، ويختم المصدر في x_lead_gen_source.
  • يكتشف اختياريًا صنّاع القرار ويربطهم بشركاتهم — فقط عند تفعيل ذلك صراحةً.
  • يعمل يوميًا ضمن حدود يومية وحدود تكلفة صارمة، مع تدوين كل قرار في سجل التدقيق.

ما الذي لا يقوم به

  • إنه ليس وحدة الإثراء (#2). الإثراء يُكمل السجلات الموجودة؛ أما توليد العملاء فيُدخل سجلات غير موجودة بعد.
  • لا يُرسل أي تواصل — يكتفي بإنشاء السجلات.
  • لا يضمن جودة البيانات؛ توقّع اسم الشركة وموقعها الإلكتروني بموثوقية أعلى بكثير من الرقم الضريبي.
ℹ️ توقّعات صادقة (يُرجى قراءتها)

بوجود مفاتيح الواجهات الصحيحة يجد هذا النظام الشركات بموثوقية. أمّا جانب صنّاع القرار (الأشخاص) فمحدود عمدًا اليوم — فمعظم مزوّدي بيانات التواصل غير مُنفَّذين بعد، وLinkedIn مؤجَّل (انظر القسم ٤). تعامَل مع تغذية الشركات كقائمة «شركات مقترحة» يراجعها إنسان.

٢.قبل أن تبدأ — المتطلبات

  • تثبيت الوحدة الأساسية. تعتمد على era_crm_ai_agents_base — وهي الاعتماد الوحيد الإلزامي.
  • توفّر مكتبة requests على الخادم (تأتي مع أودو).
  • صلاحية مدير. الإعدادات وقائمة المصادر مرئية فقط لمجموعة «مدير وكلاء الذكاء الاصطناعي»؛ ويرى مندوبو المبيعات المصادر للقراءة فقط.
  • مفاتيح الواجهات في بيئة الخادم لأي مصدر تستخدمه — وليس في قاعدة البيانات أبدًا (القسم ٤).
⚠️ كل شيء مُعطَّل افتراضيًا — وذلك عن قصد

عند التثبيت الجديد يكون المفتاح الرئيسي era_crm_ai_agents_lead_gen.enabled معطّلاً، وكل المصادر الـ18 المزروعة غير نشطة (active = False)، وجلب صنّاع القرار معطّلاً. لا شيء يتصل بالشبكة أو يُنفق مالًا أو ينشئ سجلات حتى يفعّله المدير. هذا هو الموقف «المراجعة أولًا» الذي يتطلبه نظام حماية البيانات (القسم ١٠).

٤.تفعيل مصادر البيانات

المصدر هو خدمة بيانات خارجية واحدة. يستعلم المحرّك من المصدر فقط عند تحقّق الشروط الثلاثة:

  1. نشِط — مُفعَّل active = True (كل شيء يأتي غير نشط).
  2. المفتاح موجود — متغيّر البيئة المذكور في env_key_param يُحلّ إلى قيمة على الخادم. السر لا يُخزَّن في أودو أبدًا — فقط اسم المتغيّر.
  3. ضمن النطاق — مصادر صنّاع القرار تتطلب أيضًا تفعيل fetch_decision_makers.

المصدر النشِط بلا مفتاح يُتخطّى — وليس بصمت: تُكتب علامة تدقيق blocked (ما لم تكن السياسة silent). تُدار المصادر من توليد العملاء ← المصادر.

💡 كيف تُفعّل مصدرًا

١) ضَع المفتاح في بيئة الخادم باسم المتغيّر الذي يذكره المصدر (مثل ERA_LEADGEN_SERPAPI_KEY) وأعِد تشغيل الخادم. ٢) افتح المصدر وتأكّد من المفتاح = ✓ وفعّل نشِط. ٣) تأكّد أن المفتاح الرئيسي مُفعَّل.

⚠️ مصادر اكتشاف الأشخاص هي المحدودة

المزوّدون الذين يحوّلون «شركة» إلى «شخص باسمه للاتصال» هم تحديدًا غير النشطين بعد. خطّط حول اكتشاف الشركات اليوم.

٥.تشغيل عملية اكتشاف — يدويًا

  1. اضبط الاستهداف في الإعدادات (مثل Construction / Riyadh, Jeddah).
  2. فعّل مصدرًا عاملًا مع توفّر مفتاحه (القسم ٤) — مثل SerpAPI أو OpenCorporates.
  3. فعّل المفتاح الرئيسي. اترك جلب صنّاع القرار معطّلًا لتشغيل خاص بالشركات.
  4. شغّل عملية — نفس مسار الكود للمجدوِل.
  5. اعثر على النتائج في CRM: الشركات الجديدة تحمل الوسم by_lead_generator_agent وختم x_lead_gen_source. استخدم توليد العملاء ← السجلات الخارجية المصدر، مجمّعة حسب المصدر.
ℹ️ آلية «التسلسل الشلالي» باختصار

يجرّب المحرّك المصادر المؤهّلة حسب الأولوية ويتوقف عند أول مصدر يعيد نتائج. توقّع حفنة شركات لكل تشغيل لا المئات.

٦.التشغيل التلقائي — المجدوِل اليومي

الإجراء المجدوَل «Lead Generation: Scheduled fetch» يعمل مرة يوميًا ويستدعي نفس نقطة الدخول دون إشراف.

  • يعمل بحساب مخصّص غير خارق الصلاحيات — روبوت توليد العملاء (الدخول lead_gen_bot) — كي يلتزم العمل بقواعد الوصول العادية.
  • محكوم بالمفتاح الرئيسي — إن كان معطّلًا يخرج فورًا.
  • يحترم الحدّين (القسم ٨).
  • لا يفشل أبدًا — أي حجب من الحارس يصبح تخطّيًا مع توثيق.
ℹ️ بعد التثبيت

تتطلب الإجراءات المجدوَلة الجديدة إعادة تشغيل كاملة للخادم كي تُسجَّل.

٧.التسليم إلى الإثراء

لا يستدعي توليد العملاء وحدة الإثراء مباشرة — فالتسليم غير مباشر وبلا اعتماد. كل سجل مُنشأ يكون مُسبقًا موسومًا (by_lead_generator_agent) ومختوم المصدر (x_lead_gen_source)؛ وهذا الوسم/الختم هو التسليم. وحدة الإثراء (#2)، عند وجودها، تمسح هذه السجلات وفق جدولها الخاص. لا استدعاء مباشر ولا اقتران.

٨.الحدود والتحكّم بالتكلفة

الحد اليومي للسجلات (…daily_cap، الافتراضي ٥٠)

يحدّ السجلات المُنشأة يوميًا، ومزدوج التطبيق: قبل كل استدعاء مصدر (لا إنفاق إن بُلغ الحد) ومجددًا عند كل إنشاء. آمن بالفشل: 0 = بلا حد؛ الغياب = يحظر.

حدّ التكلفة الشهري (على مستوى المنظومة)

محدود بـera_crm_ai_agents.monthly_cost_cap (الافتراضي 100.0 دولار). يعيد المحرّك فحصه قبل كل استدعاء مصدر. يسجّل كل تشغيل نصفي التكلفة: المصدر (usage_type = source_api) والذكاء (usage_type = llm).

عند بلوغ حدّ

  • تشغيل يدوي تجاوز حدّ التكلفة: يفشل سريعًا برسالة واضحة.
  • تشغيل مجدوَل تجاوز حدًّا: يتخطّى مع توثيق (cost_cap_exceeded) وينتهي بنظافة.

٩.التدقيق والمراقبة

كل قرار يُكتب في سجل التدقيق غير القابل للتعديل (وكلاء CRM الذكية ← الإعداد ← سجل التدقيق، للمدير فقط):

نوع الحدثمتى
external_contactإنشاء شركة/صانع قرار (يرتبط بالسجل؛ ولا يُخزَّن اسم الفرد).

💡 فحص صحّة سريع

كثرة صفوف blocked تعني أن مصادر نشطة تفتقد مفاتيحها. التشغيل السليم يُظهر «بداية تشغيل»، ومحاولات، وصفوف external_contact، و«نهاية تشغيل».

١٠.حماية البيانات والامتثال

⚠️ اقرأ قبل تفعيل اكتشاف صنّاع القرار

اكتشاف صنّاع القرار يعني معالجة بيانات شخصية لأفراد لم يوافقوا، كما يُرسل الاستخراج محتوى المصدر إلى مزوّد ذكاء اصطناعي دولي. يجب مراجعة أساس قانوني واعتماده من الجهة القانونية/مسؤول حماية البيانات قبل التفعيل.

الوحدة مصمَّمة للامتثال لكنها لا تدّعيه:

  • الافتراضات متحفّظة — المفتاح الرئيسي وجلب الأشخاص وكل مصدر مُعطَّلة عند التثبيت.
  • جلب الأشخاص خلف مفتاح منفصل كي لا يُفعَّل سهوًا.
  • يُخزَّن الأفراد كجهات اتصال مرتبطة كي يُطبَّق عليهم الاحتفاظ/المحو على حدة.
  • تُوسَم حركة البيانات عبر الحدود في التدقيق.
  • إعدادات موقف الإشعار/الموافقة تُوثّق موقفك؛ والامتثال (#1) يفرض «لا تواصل دون موافقة» لاحقًا.
⚠️ التفعيل ليس امتثالًا بذاته

تفعيل المفاتيح لا يجعل السلوك مشروعًا. تُوجد الافتراضات المتحفّظة كي يكون القرار متعمَّدًا ومُراجَعًا. لا يوجد مرجع PDPL معتمَد لمجموعة Era مُضمَّن؛ تلك المراجعة مسؤوليتك.

١١.استكشاف الأخطاء / الأسئلة الشائعة

«فعّلتها لكن لا تظهر عملاء.»

غالبًا لا يوجد مصدر مؤهّل. تحقّق: هل من مصدر نشِط؟ هل المفتاح = ✓ (المتغيّر مضبوط والخادم أُعيد تشغيله)؟ هل هو مصدر شركات (مصادر التحقّق لا تعمل في الاكتشاف)؟ هل بُلغ الحد اليومي؟ يُظهر التدقيق صفوف blocked أو cost_cap_exceeded التي تفسّر ذلك.

«مزوّد معيّن لا يعمل.»

Apollo/Lusha/RocketReach/SignalHire وLinkedIn غير مُنفَّذة بعد (القسم ٤). السجلات السعودية تحتاج متغيّر …_URL. بحث الويب يحتاج المفتاح (وGoogle CSE معرّف …_CX). المصدر النشِط بلا مفتاح يسجّل blocked.

«المجدوِل اليومي لم يعمل / لم ينشئ شيئًا.»

(١) المفتاح الرئيسي معطّل؛ (٢) لم يُعَد تشغيل الخادم بعد التثبيت؛ (٣) بُلغ حدّ (cost_cap_exceeded). المجدوِل لا يرمي خطأ — ينتهي دائمًا تاركًا أثرًا.

«بلغت الحد اليومي.»

متوقّع وآمن. ارفع …daily_cap، أو اضبطه 0 لبلا حد (لا يُنصح مبكرًا)، أو انتظر اليوم التالي.

«شركة جديدة بدت محذوفة كتكرار.»

يطابق منع التكرار على البريد أو النطاق أو الرقم الضريبي أو الاسم+المنطقة؛ والاسم وحده لا يحجب أبدًا. في وضع skip لا يتغيّر شيء؛ استخدم update لملء الحقول الفارغة.

«هل يمكن أن يُسرّب استدعاء مصدر مفتاحنا إلى السجلات؟»

لا — عند الفشل يُسجَّل المضيف ونوع الخطأ فقط، لا الرابط ولا سلسلة الاستعلام ولا المفتاح.

١٢.مسرد المصطلحات

  • المصدر / المزوّد — خدمة بيانات خارجية واحدة.
  • وجود المفتاح — يُستخدم المصدر فقط عند تحلّل متغيّره؛ والسر لا يُخزَّن، بل الاسم فقط (env_key_param).
  • التسلسل الشلالي — تجربة المصادر بالأولوية والتوقف عند أول مصدر يعيد نتائج.
  • التخطّي مع التوثيق — تخطّي خطوة وكتابة علامة تدقيق بدل الفشل؛ ليس بصمت أبدًا.
  • التطبيق المزدوج — فحص الحد اليومي قبل الجلب ومجددًا عند الإنشاء.
  • التسليم غير المباشر — تمرير السجلات للإثراء عبر الوسم وختم المصدر فقط.
  • روبوت توليد العملاء — الحساب المخصّص غير خارق الصلاحيات الذي يعمل به المجدوِل.
